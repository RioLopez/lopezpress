# 修订历史（版本回滚）

> 状态：Implemented（第 51 轮）｜关联：`docs/COMPETITIVE_GAP.md` G-2
> 最后更新：2026-10-23

## 1. 背景

编辑文章是**覆盖式**的：`UpdatePost` 直接把新标题/正文写回，旧内容当场消失。写错一段、误替换、粘贴覆盖之后**没有任何回头路**。WordPress / Ghost / Halo 全都有修订历史，这是"敢不敢长期用它写东西"的分水岭。

## 2. 目标与非目标

**目标**

- 每次保存前自动留一份**旧版本**快照（标题 / 正文 / 状态 / 谁改的 / 何时）。
- 每篇最多保留 **20 份**，超出按时间淘汰最旧的（低配机不接受无限增长）。
- 能列出历史、能一键恢复。恢复本身也产生一条快照（可再回退）。

**非目标**

- 不做逐行 diff（前端 diff 库会显著加大包体，与"前端 3 个依赖"冲突）。
- 不做定时自动保存的版本（那是另一件事）。
- 不记录标签/分类/封面的历史（只保证正文不丢；这几项改动风险低）。

## 3. 数据模型

```
post_revisions
  id, post_id(index), title, body, status, editor_id, created_at
```

新表 → 走 AutoMigrate 的"仅创建不存在的表"路径，无需手工迁移。

**容量估算**：20 份 × 平均 8 KB 正文 × 1000 篇 ≈ 160 MB 上限，且只增不删的只有最近 20 份；SQLite 单文件可接受。若站主在意，关闭开关后不再记录（`site_config` 不加开关，保持简单；淘汰策略已足够）。

## 4. API

| 端点 | 说明 |
|---|---|
| `GET /api/posts/{id}/revisions` | 列出该文历史（新的在前，最多 20 条，不含正文以外的敏感字段） |
| `POST /api/posts/{id}/revisions/{revID}/restore` | 用该版本覆盖当前正文；**状态不变**（不绕过审核状态机） |

权限：与"编辑文章"一致（作者本人 / admin / root），沿用 `UpdatePost` 的判定，不另写一套。

## 5. 验收标准（EARS）

- **AC-1.1**：WHEN 修改文章正文并保存 THEN 旧正文进入历史，列表可查到
- **AC-1.2**：WHEN 连续保存 25 次 THEN 只保留最近 20 份（最旧的被淘汰）
- **AC-1.3**：WHEN 点「恢复」某版本 THEN 当前正文变为该版本内容，且**恢复前的版本也进了历史**
- **AC-1.4**：WHEN 恢复 THEN 文章状态、分类、标签、封禁状态均不变
- **AC-1.5**：WHEN 非作者的非管理员调用 THEN 403
- **AC-1.6**：WHEN 文章不存在 / 版本不属于该文章 THEN 404

## 6. 边界

| 情况 | 行为 |
|---|---|
| 内容无变化地保存 | 仍留一份快照（简单优先，20 条上限兜底） |
| 恢复一条早已被淘汰的版本 | 404 |
| 恢复后文章处于 banned | 由 `UpdatePost` 的封禁冻结规则拦截（root 除外） |
| 数据库体积 | 每篇 ≤20 份，超限淘汰 |

## 7. 测试要点

- 保存两次 → 历史 2 条且内容为旧值；
- 保存 25 次 → 只留 20；
- 恢复 → 正文回到旧值、状态不变、历史 +1；
- 越权 403、跨文章 revID 404。
