# 决策 0005：图片所有权用数据不变式表达，缩略图用库内队列

> 时间：2026-10-24（第 77–78 轮）｜状态：Accepted｜规格：`docs/specs/36-media-library.md`

## 背景

第 14 轮的"图片管理"只是 `os.ReadDir` + 按文件名删文件：没有归属、没有引用关系、没有上限，文件名还带着上传时间戳（可枚举）。随着用户开始互相引用配图，四个问题同时出现：

1. 用户传错图删不掉（删了会破别人的文章，不删自己难受）；
2. 同一张图被反复上传，磁盘上存多份；
3. 全站没有磁盘上限，1 GB 的 VPS 一天就能塞满；
4. 图库列表直接加载原图，几十张就卡。

用户对此给出的约束是明确的一句话：

> "用户删了图，哪怕我们是假删除，至少也不能再给别的用户使用了，这个是所有权的问题，是侵权的。"

这句话决定了技术方案：**它不是一个流程要求，而是一个必须由数据结构保证的不变式。**

## 决策

### D1 所有权：`live_key` 轮换，而不是"记得过滤已删"

`upload_files.live_key` 上加唯一索引，三种取值：

| 状态 | `live_key` | 含义 |
|---|---|---|
| 活跃 | `sha256`（64 位十六进制） | 可被去重命中、可被任何人复用 |
| 已撤下 | `d:<id>` | 文件仍在磁盘上，但**任何按 live_key 的查询都查不到它** |
| 历史文件 | `legacy:<name>` | 第 77 轮之前就在盘上的文件，无归属 |

去重只有一个入口——按 `live_key` 查。于是"撤下的图不会复活给下一个人"是**结构保证**，不依赖任何一层记得判断。同理，恢复（restore）时若同 hash 已有活跃行，返回 409 而不是合并。

### D2 软删不能用 `gorm.DeletedAt`

`UploadFile.DeletedAt` 是普通 `*time.Time`。原因：撤下之后，**已经发表的文章里还嵌着这张图**，静态文件服务必须继续提供它。用 GORM 的软删标记会让 `GET /uploads/{name}` 也看不到它 → 文章破图 → 让文章作者替上传者受罚。

所以：列表接口自己加 `deleted_at IS NULL`，文件服务完全不看这个字段。这是一处**刻意的不一致**，改动前先读本节。

### D3 去重选"物理合并 + 引用计数"

被否决的方案是"只提示库里已有，仍各存一份"：省不了空间，而且一旦别人删了引用，你的文章仍然指向同一份文件——反而更难说清归属。物理合并之后，`upload_refs` 记录"哪篇文章引用了哪张图"，`ref_count` 是缓存列（用相关子查询重算），删帖/改帖时做差集同步。

### D4 三层配额，全站统计含软删行

单文件分级（正文 5 MB / 头像 512 KB）、单账号 20 MB、全站 500 MB，全部可在后台改。**全站统计包含已撤下的行**，因为那些字节确实还占着磁盘；个人统计只算活跃行——否则"我删了图为什么额度没回来"会变成客服问题。

顺序固定为 **去重 → 配额 → 写盘**：配额在写盘之前（被拒的请求不留半截文件），去重在配额之前（复用不产生新字节，不该计额度）。

### D5 文件名不可枚举

`crypto/rand` 16 字节 → base62 → 定长 22 字符（`models.NewOpaqueID()`），文件名 = `<id><ext>`。URL 不再泄露上传时间、上传者、原文件名。原文件名单独存 `original_name`（仅供后台溯源与展示）。

### D6 缩略图：队列的待办状态在数据库里

`upload_files.thumb_status`（`pending` / `ready` / `skip` / `failed`）是唯一真相。内存 channel 容量 32，只做"有新活"的唤醒，**满了直接丢弃**——因为行仍是 pending，下次扫描会补。

消费侧：单 goroutine，每张之间暂停 150 ms。启动扫描 200 条封顶，另有一个 **30 秒 sweep** 补积压（没有 sweep 的话，积压超过 200 张就只能靠重启才动）。

规格：长边 480、CatmullRom、不透明→JPEG q82 / 有透明→PNG（JPEG 会把透明像素变黑）。三种情况判 `skip`：长边 ≤480 且 ≤96 KB、重编码后反而更大、格式解不开。**解码上限 24 MP，比上传校验的 40 MP 更严**——后台 goroutine OOM 会杀掉整个进程，而没有缩略图只是列表慢一点。

### D7 新依赖 `golang.org/x/image`（对"不加重依赖"红线的一次显式豁免）

`AGENTS.md` 红线 1 是"不换框架、不加重依赖"。这里加 `golang.org/x/image`（`draw` + `webp`）需要理由：

- 官方扩展库、纯 Go、无 CGO，二进制 +0.5 MB（17.9 → 18.4 MB）；
- 标准库只有最近邻缩放，缩略图质量不可接受；
- 顺带修掉一个既有缺陷：WebP 之前 `width/height` 恒为 0，图库里一直显示 `—`。

**WebP 上传校验仍走魔数**，不用这个解码器当门槛——它拒绝动画 WebP，用它校验会挡掉合法的动态图。

## 代价与已知不足

- 缩略图 `failed` 是终态，不自动重试（需管理员手工清 `thumb_status`）。
- `upload_refs` 只在通过 API 保存/删除文章时同步，直改库会产生孤儿引用；spec 36 §8 提到的"夜间全目录对账"**未实现**。
- 全站配额用 `SUM(size)` 实时算，图片上万时会有一次全表扫描（当前规模无影响）。
- 硬删会返回 `affected_refs` 但不阻止删除——这是刻意的：管理员删违规图优先于保护引用。
