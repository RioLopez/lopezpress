# 决策 0004：CORS 白名单收紧

## 背景

原 `internal/router/router.go` 硬编码 `middleware.CORS("*")`，
即生产环境默认允许任意来源携带任意请求。这违背审计要求
"生产环境务必收紧 CORS"。

## 决策

1. **来源可配置**：`CORS_ORIGINS` 环境变量控制允许的来源列表
   （逗号分隔），`*` 表示全开（仅 dev 默认）。
2. **`*` 与 credentials 永不同时出现**：中间件在 wildcard 模式下
   **不**发送 `Access-Control-Allow-Credentials: true`，
   因为 `ACAO=* + credentials` 等价于"允许任意来源携带 cookie"。
3. **prod 严格校验**：`APP_ENV=prod` 且 `CORS_ORIGINS=*` 时，
   `ValidateSecurity()` 直接阻断启动。
4. **dev 警告**：`APP_ENV=dev` 且 `CORS_ORIGINS=*` 时，启动时
   向 stderr 打印 `WARN`，不阻断。

## 实现落地

| 改动点 | 文件 | 内容 |
|---|---|---|
| `CORSOrigins` 字段 | `internal/config/config.go` | `envOr("CORS_ORIGINS", "*")` |
| `ValidateSecurity` 检查 | `internal/config/config.go` | prod 时 `*` 阻断 |
| 中间件改造 | `internal/middleware/middleware.go` | wildcard 不发 credentials |
| router 改造 | `internal/router/router.go` | `middleware.CORS(cfg.CORSOrigins)` |
| 单测 | `internal/middleware/middleware_test.go` | `TestCORSWildcardOmitsCredentials`、`TestCORSRestrictedSetsCredentials` |
| 文档 | `.env.example` | 加 `CORS_ORIGINS` 注释 |

## 推荐配置

| 场景 | `APP_ENV` | `CORS_ORIGINS` |
|---|---|---|
| 本地开发 | `dev` | `*`（默认） |
| 生产单一域名 | `prod` | `https://blog.example.com` |
| 生产多域名 | `prod` | `https://blog.example.com,https://admin.example.com` |
| 生产仅后端同源 | `prod` | 留空（不匹配任何 origin，浏览器仍允许同源请求） |

## 验证

```bash
# 1) prod + * 必须阻断
APP_ENV=prod CORS_ORIGINS='*' go run ./cmd/server
# 期望：security config invalid: APP_ENV=prod: CORS_ORIGINS must be an explicit origin list

# 2) dev + * 警告不阻断
APP_ENV=dev CORS_ORIGINS='*' go run ./cmd/server
# 期望：stderr 出现 WARN: dev mode with CORS_ORIGINS=*

# 3) prod + 显式来源允许
APP_ENV=prod CORS_ORIGINS='https://blog.example.com' go run ./cmd/server
# 期望：正常启动；curl -H "Origin: https://blog.example.com" -I 见 ACAO=echo
```

## 残余风险

- **来源拼写错误**：若 `CORS_ORIGINS` 拼错（少了 `https://`），浏览器
  会拒绝跨域请求，但不影响同源部署。建议上线前用 curl 验证。
- **`Vite dev server` 的跨域**：本地开发时 `:5173` 调 `:8080`，
  用 `*` 全开即可，不影响生产。
- **未来 S3 / 图床**：若引入 S3 签名 URL 或外部图床，需在前端
  `web/vite.config.ts` 加 `server.proxy` 走同源，无需再放 CORS。
