# 模板 03 — 修 bug:复现 → 定位 → 修复 → 回归

## 何时用
用户报告运行时报错、行为不符预期、测试失败时。**带着日志/复现步骤来,不要只说"有 bug"**。

## 提示词正文(粘贴区)

```
按 lopezpress 的 AI 协作标准修复 bug。

【现象】
<粘贴:报错信息 / 复现步骤 / 期望 vs 实际>

【执行要求】
1. 先取证再动手:
   - 运行态问题先看服务日志(data/server.log、backend.log)和进程状态
   - 区分「服务没起 / 配置没生效(改了 .env 没重启)/ 真代码缺陷」三类
   - 定位到 文件:行号 级根因,贴出证据链,不接受"可能是"
2. 汇报根因和修复方案(3-5 行),方案涉及破坏性操作(停服务/删文件/改 DB)的,
   先列清单等确认再执行。
3. 修复时必须:
   - 先写/补一个能复现问题的回归测试(测试先行),再修
   - 检查是否触发红线 R1-R10(尤其迁移/权限/限流/路径逃逸)
   - 同类问题全局搜一遍(同一个错误模式别处有没有)
4. 完成后:门禁五命令全绿 + 复现场景验证通过(贴前后对比证据)+ 记录:
   PROGRESS 或 memory 日志记根因(根因比修复动作更值得记)。
```

## 预期产出
- 根因定位(文件:行号 + 证据链)
- 回归测试 + 修复
- 复现验证的前后对比
- memory/HANDOVER §7 陷阱记录(如果是新类型坑)
