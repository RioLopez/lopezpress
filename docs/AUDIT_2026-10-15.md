## 1. P0 — 必须修（安全越权 / 用户可见 bug / 功能断裂）

### P0-1 `ResetPassword` 越权 → admin 可接管 root 账号 ⚠️ 最严重

**事实**：
- `internal/services/accounts.go:385` `func (s *Service) ResetPassword(ctx context.Context, id, password string) error` —— **没有 actor 参数**，service 层完全不校验调用者身份。
- `internal/handlers/accounts.go:163` handler 只调 `requireAdmin`（= admin-or-root）。

**后果**：任何 admin 调 `POST /api/users/{root_id}/reset-password` 即可设置 root 的新密码，然后用新密码登录 root，完整接管站点。这是教科书式权限提升链（privilege escalation）。

**对照**：`UpdateUser`/`DeleteUser` 都有 actor + 层级校验，唯独 `ResetPassword` 漏了——因为它没有复用 `roles.go` 的 `canManageUser`（见 P1-1）。

**修法**：签名加 `actor models.User`，入口处 `if !canManageUser(actor, target) { 403 }`；补测试「admin 重置 root 密码 → 403」。

---

### P0-2 `DeleteUpload` 越权 → 任意登录用户可删他人上传

**事实**：`internal/handlers/upload.go:54-61` `DeleteUpload` 仅校验文件名合法性，**无属主、无 requireAdmin**；`services.go:2251-2264` `DeleteLocalUpload` 直接 `os.Remove`。

**后果**：普通 user 可 `DELETE /api/uploads/{任意文件名}` 删掉站图上他人上传的图片（图片无属主记录，事后无法追溯谁删的）。

**对照**：同类"管理面"端点（`/api/categories`、`/api/users/*`、`/api/trash`）全部有 `requireAdmin`，唯独上传删除没有——明显的遗漏不对称。

**修法**：`DeleteUpload` 加 `requireAdmin`（图片库是管理功能，不是用户功能）；或给 `LocalUpload` 记录上传者 ID 并做属主校验。推荐前者（简单且与现有模型一致）。

### P0-3 i18n key 拼错 → 用户看到原始键名（第 25 轮引入）

**事实**：
- 代码用顶层 key：`web/src/pages/ListPage.tsx:213`、`ReadPage.tsx:224` `{t(`statusLabel.${p.status}`)}`；`PersonalCenterPage.tsx:282-284` `t('statusLabel.pending')` 等。
- i18n 只定义了 `admin.statusLabel.*`：`web/src/core/i18n.tsx:754-760`（zh）/ `:1236-1242`（en）。
- `t()` 未命中时**原样返回 key**（`i18n.tsx:1514`）。

**后果**：作者/管理员在列表页、阅读页、个人中心看到的徽章文字是 **"statusLabel.pending"** 而不是"待审核"。这是第 25 轮我改 `status` → `statusLabel` 规避命名冲突时，漏改了三个调用点。

**修法**：三处 `statusLabel.` → `admin.statusLabel.`；顺手修 `i18n.tsx:265` 那条写错键路径的注释。

### P0-4 审核流闭环断裂 → "修改后重新提交"不可达

**事实**（四层全断）：
1. **意见不展示**：`review_note` 在 `core/types.ts:51` 有定义，但全 `web/src` grep 无任何页面读取。而 i18n 承诺了"作者可见"：`i18n.tsx:851` `reviewNotePlaceholder`="说明需要修改的地方（作者可见）"、`:855` `rejectHint`="作者会收到打回通知和上面的意见，可修改后重新提交"。
2. **后端不接受重新提交**：`services.go:876-883` `UpdatePost` 的 status 白名单只接受 `private`（人人）和 `published`（仅 root）——rejected 文章保存后**仍是 rejected**。
3. **无 resubmit 端点**：`ListPending`（`services.go:1195`）只收 `status = pending`，没有 rejected→pending 的转换接口。
4. **前端无入口**：`EditPage.tsx:34-62` 只透传 title/body/status/...；`PostEditor.tsx:578-597` 可见性单选只有公开/私密。

**后果**：作者被打回 → 看不到意见 → 不知道改什么 → 即使改了也无法重新进入审核队列 → 只能删掉重写。**核心卖点"多作者审核流"实际不可用。**

**修法**（三层）：
- 后端：`UpdatePost` 允许作者把 `rejected` 改回 `pending`（即"重新提交"，`in.Status == "pending" && post.Status == rejected && me.ID == post.AuthorID`）。
- 前端：`ReadPage`/`PersonalCenterPage`/`EditPage` 展示 `review_note`（用 alert/banner 样式）；`PostEditor` 对 rejected 文章显示"重新提交"按钮。
- 邮件已通（`MailReviewResult`），补齐站内展示即闭环。

### P0-5 分类/标签计数虚高（把软删 + banned + pending 都算进去）

**事实**：`services.go:1403-1420` `ListCategoriesWithCount` 用 `Table("categories")` 裸 SQL + `COUNT(posts.id)`，**绕过了 GORM 软删 scope**（回收站文章照算），也没有按 status 过滤（banned/pending/rejected 照算）。`ListTagsWithCount`（`:1424-1441`）同理，`COUNT(post_tags.post_id)` 把软删文章的关联行也数进去。

**后果**：后台分类/标签管理页显示的文章数比前台实际可见数高。客户会报"数字对不上"。

**修法**：两处都加 `WHERE posts.deleted_at IS NULL`（裸表查询需手写）+ 视产品决定是否排除 banned/pending（建议排除——"文章数"应指公开可见的）。

---

### P0-6 `writeXML` 错误路径返回 200

**事实**：`internal/handlers/feed.go:189-192`：
```go
out, err := xml.Marshal(v)
if err != nil {
    w.Write([]byte("<error>failed to render feed</error>"))
    return   // ← 没有 WriteHeader，客户端收到 200 + XML 错误体
}
```

**后果**：marshal 失败（如非法 XML 字符）时 RSS 阅读器收到 200 + 非 RRS 内容；且错误体格式与全项目 JSON `{"error":...}` 契约不一致。

**修法**：`w.WriteHeader(http.StatusInternalServerError)` + 统一 JSON 错误体。

## 2. P1 — 应该修（数据一致性 / 明显缺陷 / 架构失信）

### P1-1 `roles.go` 的集中权限层是死代码（架构失信的头号案例）

**事实**：`roles.go:35` `canManageUser` 与 `:61` `canReviewPost` **全仓零调用**（grep 确认只有定义处命中）。文件头注释却宣称 "Every 'can X do Y' decision in the service layer goes through one of these functions"。

**实际状态**：
- `UpdateUser`/`DeleteUser`/`CreateUser` 是手写 if-else 链（`accounts.go:331-382`、`:460-493`）；
- `ReviewPost`/`BanPost` 是另一套手写 if（`services.go:1005-1032`、`:1086-1096`）；
- `ResetPassword` 干脆没有校验（P0-1）。

**这正是"一个模块一个写法"的实证**：三层角色模型在第 25 轮设计了统一权限抽象，但落地时每个 service 方法各写一遍，结果漏了一个就是 P0 漏洞。

**修法**：把三个用户管理方法 + 四个审核方法全部改为调用 `canManageUser`/`canReviewPost`，删掉手写链；`roles.go` 注释改谦符（"handler 用 IsRoot/IsAdminOrRoot，service 用 canManageUser/canReviewPost"）。

### P1-2 `CreateUser` service 层不校验 actor

`accounts.go:264` `CreateUser(ctx, actor, in)` 只在"创建 admin"时查 `actor.Role`。若 actor 是普通 user 且 `in.Role = "user"`，直接创建成功。当前靠 handler 的 `requireAdmin` 兜底，但注释自称 "service 层再做完整校验，handler 可被绕过，service 是权威"（HANDOVER §7.7）——**没做到**。修法同 P1-1。

### P1-3 `DeleteUser` 与回收站文章的数据不一致

`accounts.go:485` `s.db...Model(&models.Post{}).Where("author_id = ?", id).Count(&postCount)` —— **带 GORM 软删 scope**，回收站里的文章不计入。后果：用户文章全在回收站时可成功删用户，那些文章的 `author_id` 成孤儿，`ListTrash` 的 `Preload("Author")` 得到 nil，前端回退显示 UUID。修法：`Unscoped().Count()` 或显式 `WHERE deleted_at IS NULL OR deleted_at IS NOT NULL`。

### P1-4 `DeleteBannedPermanently` 不清理 post_tags 关联行

`services.go:1229` `Unscoped().Delete(&models.Post{}, "id = ?", id)` 硬删 post，但 `post_tags` 关联行成为孤儿 → 叠加 P0-5 让标签计数继续虚高。`DeleteTag`（`:1450`）反而正确清理了关联。修法：硬删前先 `tx.Where("post_id = ?", id).Delete(&models.PostTag{})`，与 DeleteTag 对齐。

### P1-5 `WithOptionalAuth` 无 must_change_password 门

`handlers/auth.go:293-312` 的 `withOptionalAuth` 未复制 `WithAuth`（`:255-258`）的首启锁定。后果：被要求改密的用户仍可带着旧 token 浏览全部读接口（列表/归档/分类/标签），锁定只覆盖了写操作。修法：`withOptionalAuth` 也查 `MustChangePassword`，命中则按零值 user 放行（只给公开数据）或 403。

### P1-6 `ImportBackup` 无 MaxBytesReader

`handlers/admin.go:152-156` 对整个备份 JSON 体 `Decode` 无大小上限（对比 `upload.go:15` 有 2MB 封顶）。超大 body 可撑爆 1.5 GB 内存。修法：套 `http.MaxBytesReader`，超限返 413。

### P1-7 `RestoreSnapshot` 零审计

`handlers/admin.go:171-188` 破坏性数据库恢复无 `recordAudit`（对比 `ImportBackup` 有）。安全事件里"谁恢复了备份"必须可查。修法：补一行 `recordAudit`。

### P1-8 双重审计（moderation 4 个操作）

`review_post`/`ban_post`/`send_back_post`/`delete_banned` 在 handler（`moderation.go:58/74/112/127`）和 service（`services.go:1072/1109/1159/1232`）**各记一条** action_log，detail 文案还不同。修法：删 handler 侧 4 行（service 侧信息更全），保留 service 为唯一审计点。

### P1-9 前端 5 处"失败时弹成功文案"

`PersonalCenterPage.tsx:230/:271`（`t('list.visibilityUpdated')`="可见性已更新"）、`SettingsPage.tsx:120`（`t('profile.saved')`）、`:45`（`t('imageLib.deleted')`）、`AdminSitePage.tsx:74`（`t('site.saved')`）。catch 块里错误提示用了成功语义的 key。修法：各自换成对应失败 key 或复用 `admin.failed`。

### P1-10 前端"重试"是死按钮

`PersonalCenterPage.tsx:139/:299` `onClick={() => setPage((p) => p)}` —— state 引用不变，不触发 effect，"重试"点了没反应。修法：`setPage(0)` 或引入 `reloadKey` state。

### P1-11 `ListPage` 计数渲染无意义

`ListPage.tsx:198` `t('common.count', { from: String(items.length), to: String(items.length), ... })` from/to 同值 → 显示 "20–20 / 37"。修法：from 用 `(page-1)*size + 1`。

### P1-12 前端 `canManage` 未排除"自己"

`AdminUsersPage.tsx:85-88` `canManage` 对普通用户恒返 `true`，未排除操作者本人（后端 `roles.go:39` 明确 self-protection）。后果：对自己行的"禁用/删除"按钮可点，点了必被后端 403。修法：`canManage` 加 `u.id !== me.id`。

### P1-13 密码策略三套标准

前端 `RegisterPage.tsx:33`、`AdminUsersPage.tsx:366/:441` 用 `< 6`（且错误消息是 `t('auth.empty')`"请填写完整信息"，文不对题）；`PersonalCenterPage.tsx:397`、`ChangePasswordPage.tsx:45` 用 `< 8`；后端统一 ≥8（`accounts.go:268/:386`、`services.go:333`）。修法：前端全部统一 ≥8 + 独立错误 key。

### P1-14 `UpdatePost` 的 private 分支不限制角色

`services.go:877-879` `case in.Status == models.PostPrivate: post.Status = in.Status` —— 任何角色可把**任意自己的**文章改成 private，包括把 pending/rejected 改成 private。后果：作者可用"改私密"绕过审核队列（内容仍不可见，但脱离了审核流，且 private 文章不计入任何队列）。修法：private 分支加 `me.ID == post.AuthorID || me.Role == RoleRoot`，且禁止从 pending 直接转 private（或明确允许并在文档记录取舍）。

| 徽章显示 "statusLabel.pending" | 🔴 P0-3，一眼可见的粗糙，直接影响"专业度"印象 |
| admin 能重置 root 密码 | 🔴 P0-1，若客户方有多个管理员，这是架构级信任问题（"我的超管账号不安全"） |

| 无评论系统 | 🟢 已记录为增强方向，不影响当前定位（个人/小团队博客） |

### 4.3 终端用户视角

| 角色 | 体验断点 |
|---|---|
| 作者（user） | 发文后不知道审核到哪了（无站内状态）；被打回看不到意见；改了不能重新提交；最终只能删掉重写 |
| 作者（admin） | 自己的文章要 root 审，但看不到 root 何时处理（无通知，除非配 SMTP） |

| 访客 | 无感知（读接口正常）✅ |
