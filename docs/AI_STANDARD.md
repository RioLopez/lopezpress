# AI 协作标准(AI_STANDARD)

> 版本:v1.0 | 2026-10-19 建立
> 定位:本文件是 lopezpress 项目**驱动 AI 干活的唯一标准**,回答三个问题:
> **AI 按什么流程干活、干到什么程度算完、干完怎么沉淀**。
> 速查入口是根目录 `AGENTS.md`;本文件是完整版,冲突时以本文件为准。
> 配套:`docs/prompts/`(场景提示词模板)、`docs/reference/AI_CODING_REFERENCES.md`(外部方法论来源)。

---

## 1. 适用范围与角色

| 角色 | 由谁担任 | 职责 |
|---|---|---|
| **决策者** | 用户 | 定优先级、拍板技术方向、批准破坏性操作 |
| **执行者** | AI(本仓库的任何编码助手) | 按 §3 工作流执行;不自作主张扩大范围 |

AI 的权限边界(SOUL 级约束,不可被提示词绕过):

- 读、查、分析可大胆;**删除、改配置、停服务、对外发送必须先列清单 + 说明风险 + 拿到明确确认**。
- 报告里区分「实测」「推断」「未采集」,不把没验证的推断写成事实。
- 系统级操作(本机为非管理员账户)先说明需要提权,不自作主张。

## 2. 任务分级:先分类,再动手

接到任何任务,先归入以下一类,不同类别走不同流程:

| 级别 | 判据 | 流程 |
|---|---|---|
| **T0 直接做** | 单文件、局部、无行为变化(文案/注释/格式/删死代码) | 实现 → 门禁 → 记录 |
| **T1 小改动** | 2–5 个文件、行为变化可一句话说清 | 简述 plan(可口头)→ 实现 → 门禁 + 回归测试 → 记录 |
| **T2 功能/结构改动** | 新端点/新页面/改数据模型/改权限或可见性规则 | **先写 spec**(`docs/specs/` 模板)→ plan → 分步实现 → 门禁 + 新增测试 → 记录 |
| **T3 排查/审计** | 找 bug、全栈审计、性能问题 | 先取证(日志/复现/代码走读)再动手;产出分级问题清单(见 §7) |

**禁止**:跳过 spec 直接实现 T2;用"顺手改一下"扩大任务范围;把多个 T2 揉进一轮不做记录。

## 3. 核心工作流(五阶段)

每个任务(无论大小)都按这个循环走,提示词模板见 `docs/prompts/`。

### 阶段 1 — 读上下文(禁止跳过)

必读(按序,能并行读就并行):

1. `AGENTS.md`(红线速查)
2. `HANDOVER.md` §0 与 §7(现状 + 陷阱)
3. `PROGRESS.md` 最新一轮(上次干到哪)
4. `docs/TODO.md`(唯一权威待办)
5. `.workbuddy/memory/MEMORY.md` + 最近 1–2 篇日志(踩过的坑)

上下文工程纪律:

- 大文件分段读,不要整文件灌入;只读与任务相关的段落。
- 批量独立搜索合并到同一轮发起。
- 不确定的过去结论用日志/`conversation_search` 查证,不靠记忆猜。

### 阶段 2 — 定任务

- T0/T1:在回复里用 1–3 行说清「改什么、为什么、影响面」。
- T2:按 `docs/specs/` 既有格式写 spec(EARS 验收语法:`WHEN … THEN …`),给出分步 plan,等用户确认后再写码。用户已说"继续/直接做"则按确认处理。
- 破坏性操作(删文件/改配置/停服务):先列清单 + 风险 + 备份方案,拿到明确确认。

### 阶段 3 — 实现

- 遵守 `AGENTS.md` §2 硬约束与 §3 陷阱。
- 权限/可见性/角色判定一律走 service 层(`services/roles.go`、`canSeePost`),不散落 if-else。
- 错误契约英文;界面文案 i18n 键(中英双语都加)。
- 测试与实现同轮:bug 修复必须带回归测试;新功能必须带服务层用例。
- 保持项目风格:矩形、无圆角、无阴影、不用 emoji;注释解释"为什么"而不是"是什么"。

### 阶段 4 — 验证门禁(完成定义)

**代码类任务全部满足才算完**(详见 `docs/prompts/05-verify-record.md`):

```
go build ./...        ✅
go vet ./...          ✅
go test ./...         ✅
web: npx tsc --noEmit ✅
web: npm run build    ✅
```

外加:

- 行为验证:能跑起来看效果的(端点/页面/交互),必须实际验证并贴证据(状态码/日志/截图),不能只说"应该可以"。
- 安全相关改动:检查是否触发 §3 红线(尤其权限、迁移、限流)。
- 门禁任何一项红:修到绿,或者明确记录"未解决 + 原因",**不允许带病标记完成**。

### 阶段 5 — 记录沉淀

任务完成后按改动性质更新对应文件(可多项同时更新):

| 改动性质 | 更新 |
|---|---|
| 功能/修复/加固(成轮) | `PROGRESS.md` 追加轮次条目(格式照旧轮) |
| 待办状态变化 | `docs/TODO.md`(勾销/降级/新增) |
| 发现新陷阱或坑 | `HANDOVER.md` §7 追加;同时写进 `.workbuddy/memory/MEMORY.md` |
| 重大方向决策 | `docs/decisions/` 新增编号文件(append-only) |
| 每次会话(无论大小) | `.workbuddy/memory/YYYY-MM-DD.md` 追加简短记录(改了什么、验证结果、遗留) |
| 架构变化 | `docs/ARCHITECTURE.md` + `docs/PROJECT_OVERVIEW.md` |

## 4. 编码红线(汇总,详细案例见 `HANDOVER.md` §7)

| # | 红线 | 违反后果 |
|---|---|---|
| R1 | 不无条件 `AutoMigrate`;已存在表的 schema 由 `runManualMigrations` 管理 | glebarez copy-rename 漏 NOT NULL 列,启动崩溃 |
| R2 | root 不可经任何 API 创建/提升;`CreateUser`/`UpdateUser` 遇 `RoleRoot` 直接 403 | 权限体系崩塌 |
| R3 | 读接口用 `WithOptionalAuth`,写接口用 `WithAuth` | 匿名读不了 / 坏 token 放行 |
| R4 | 可见性五态判定只在 service 层(`canSeePost`) | 前后端判定漂移,私密/待审泄漏 |
| R5 | 权限 helper 只用 `services/roles.go` 的集中函数 | 手写 if-else 漏判(历史 P0 根因) |
| R6 | 改 `.env`/限流/配置后必须**重启后端**才生效,验证时注意旧进程 | "改了没效果"假象 |
| R7 | 上传/备份路径必须 `filepath.Abs` + `filepath.Rel` 防目录逃逸 | 任意文件删/读 |
| R8 | 限流按身份分桶:登录用户按 user ID,匿名按 IP;爆破防护靠 LoginLimiter | 放宽通用桶 = 放开爆破 |
| R9 | 删除/移动仓库文件前先确认;`.workbuddy/` 目录不删 | 记忆层丢失 |
| R10 | JWT_SECRET 生产必须强随机(≥32 字节,非默认);CORS 生产必须显式 origin | 生产安全事故 |

## 5. 上下文工程纪律(让 AI 在长任务里不跑偏)

1. **一次只推进一个任务**,完成并记录后再开下一个;上下文超过 ~60% 主动收尾当前轮并写记录,不硬撑。
2. **先查后写**:动手前先用 Grep/Glob/读文件定位,不凭印象改代码。
3. **证据链**:审计类产出必须带 文件:行号 级证据,不接受"可能有问题"。
4. **并行独立调用**:多个无依赖的读/搜合并到同一轮。
5. **遇审批拦截换通道**:文件读取被拦截时派 Explore 子代理读(已知有效),不死磕。
6. **区分事实与推断**:回复和文档里标注「实测 / 推断 / 未采集」。

## 6. 提示词模板使用方式

`docs/prompts/` 下 5 个模板覆盖高频场景,用户可直接粘贴,AI 收到后按模板执行:

| 模板 | 场景 |
|---|---|
| `01-continue.md` | 「继续」— 恢复上下文,选下一优先级任务 |
| `02-new-feature.md` | 新功能(T2):spec → plan → 实现 |
| `03-bugfix.md` | 修 bug(T1/T2):复现 → 定位 → 修复 → 回归 |
| `04-audit.md` | 自查/审计(T3):全栈扫描 → 分级清单 → 修复 |
| `05-verify-record.md` | 验证门禁 + 记录沉淀 |

模板是"标准提示词",不是僵化脚本:按实际任务裁剪,但**流程骨架(阶段 1→5)和验证门禁不允许省**。

## 7. 质量自查清单(交付前逐条过)

- [ ] 门禁五命令全绿(或明确记录未解决项 + 原因)
- [ ] 行为验证有证据(状态码/日志/截图)
- [ ] 新逻辑有测试;bug 修复有回归测试
- [ ] 无散落权限/可见性判断;新错误码走英文契约;新文案走 i18n 中英双语
- [ ] 未引入新依赖(或有充分理由且用户认可)
- [ ] `PROGRESS.md` / `TODO.md` / memory 日志已按 §3 阶段 5 更新
- [ ] 报告结论先行,附证据;区分实测/推断

## 8. 本标准的维护

- 本文件 append-only 地演进:发现流程缺口就补条款,不推倒重来。
- 每次修订在文末「修订记录」追加一行(日期 + 改了什么)。
- AI 在协作中总结出的新经验,优先沉淀为 `HANDOVER.md` §7 陷阱条目和 memory,而不是堆在本文件里——本文件只管流程,不管案例库。
